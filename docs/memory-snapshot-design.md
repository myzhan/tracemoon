# Lua 堆快照与持有关系分析

状态：已开始实现首版，下面保留完整设计与后续验收目标。首要目标是让**单次抓取的报告足够清晰，能指导排查**。
快照对比、分配位置追踪、自动判断泄漏不属于第一版。

当前实现：64 位 Linux / 标准 Lua 5.4 及 skynet v1.8.0 内置 Lua 5.4.7 的 `mem capture`，以及可在 macOS 使用的
离线 `mem report` / `mem inspect`。支持 attach 和带初始化等待的 spawn；spawn 结束会终止子进程。
对象图保存为版本化 JSON，地址作为快照内对象标识。枚举四条所属链、读取根和对象引用，
输出服务/类型统计、大对象候选、强持有路径、其他持有者和内容预览。

当前边界：5.5 尚未开放；弱键条件引用不做 ephemeron 不动点传播，终结器语义不完整；
没有强路径的对象不判断为垃圾。字符串预览固定为最多 96 字节，table 内容最多展示 8 项，
暂未开放预览长度配置。独占保留大小、完整引用者浏览、快照对比留待后续。

skynet 的 Lua 分支虽然版本号相同，但 TString 带额外 id，gcstate 偏移也不同；通过 H
符号选择独立布局，快照记录 `lua_abi`，不能按版本字符串直接套用标准布局。
共享代码缓存中的 Proto/字符串可能不在服务 GC 链内；已按 `G_SHARED` 标记补充读取，
服务私有总量排除这些对象，共享部分按地址在所选服务间去重。协作式测试导出的报告记录
`capture_method`，不会被表述为全进程同时暂停的快照。

验证：两个 vendor 的真实 C 头文件布局校验与分配器导出堆测试已在本地主机通过，
Linux 分支交叉编译/Clippy 通过。Linux 暂停恢复与完整抓取用例已加入 CI，实际执行及
真实 skynet 验收仍待完成。下面的预算和验收条款是持续约束，不能仅凭编译通过视为全部完成。

## 1. 要回答的问题

1. 哪个 skynet 服务占用的 Lua 对象内存最多？
2. 大对象是什么，容量和内容有什么特征？
3. 它从哪些根被持有，能否定位到模块字段或函数 upvalue？
4. 当前报告覆盖了多少堆，有没有未解析对象或不确定引用？

Table、String 不保存分配源码位置。不能把对象关联的函数来源说成创建位置。
可以报告 `player.lua:86` 的函数通过名为 `sessions` 的 upvalue 持有某表；
不能据此说该表在第 86 行分配。源码和 upvalue 名被裁剪时显示可用的地址/索引。

## 2. 用户体验与产物

当前命令：

```bash
tracemoon mem capture -p 12345 -o heap.tmoon
tracemoon mem capture -p 12345 --service :01000012 -o player.tmoon
tracemoon mem report heap.tmoon -o heap-report.txt
tracemoon mem report heap.tmoon -o heap-report.html
tracemoon mem inspect heap.tmoon --object 0x12345678
tracemoon mem report core.dump --exe ./skynet -o report.html
tracemoon mem report core.dump --exe ./skynet --service trace_alpha -o alpha.html
tracemoon mem inspect core.dump --exe ./skynet --object 0x12345678
```

### 直接分析 coredump

输入按文件内容识别 `.tmoon` 对象图或 Linux ELF64 core，不要求先 import。
`core.rs` 提供与活进程相同的 `ProcessMemoryReader`；通过 PT_LOAD 把虚拟地址转换为
core 文件偏移，通过 NT_FILE / AT_PHDR 还原配套 ELF 二进制的装载位置。
VM 扫描抽成接收地址区间的公共入口，再复用原有堆枚举、引用解码和报告。
Linux x86_64/aarch64 小端 core 可以在小端 64 位 Linux/macOS 主机离线分析。

`--exe` 指向匹配构建的 ELF 文件。skynet 必须保留 `H` 符号，以选择 fork 的 ABI 并
定位服务；可用的已转储 ELF note 与配套文件比较，发现不匹配就报错。不会主动打开
NT_FILE 记录的原路径；只允许从用户指定二进制恢复缺失的只读文件字节，不补写可变
数据、堆页或 BSS。动态库文件补全、压缩 core、Mach-O core 和 Lua 5.5 留待后续。
版本无法识别时允许显式 `--lua-version 5.4`；已知单 VM 地址可用 `--state`。

core 提取固定限制为 60 秒、1 GiB 请求读取、100 万对象、200 万引用。
缺页、截断、对象解码失败会标为 incomplete；无法定位 VM 时直接给出错误，不输出
看似完整的空报告。原 PID、生成时间和暂停时长当前未解析，不把文件修改时间或分析
耗时当成采集时间。core 可能停在 GC 或结构更新中，也可能已遭破坏；同样不判定垃圾
和泄漏。单次捕获结果仍受既有弱引用/终结器语义边界约束。

第一版优先 Linux x86_64 attach。Lua 5.4 先验收，再以相同测试标准扩展 5.5。
macOS 的整进程挂起、恢复语义另行验证后开放，不自动套用现有单线程 native lock。
内存命令独立于 CPU 采样器。默认暂停预算 2000 ms、对象数上限 100 万、引用数上限 200 万、
读取字节数上限 256 MiB，均可通过 CLI 调整。预算耗尽会保存 incomplete 快照并返回非零状态；
冻结前失败可能不生成快照。详情见 `mem capture --help`。

抓取保存版本化的对象图：对象 ID、地址、类型、自身大小、引用边、必要的字符串与
源码线索，以及完整性信息。恢复进程后再分析和生成默认文本报告；离线 inspect 不再
访问目标进程。默认报告可看前若干项，但对象图不按报告 top-N 截断。

字符串预览和字段名需要保留以支持可读路径，但长度有上限；被截断时保留原始长度。
快照可能包含业务数据，默认不保存大段字符串正文，预览长度应可配置。

## 3. 单次报告示例

以下数据示意报告希望提供的信息；文本报告为英文，HTML 提供中文分层视图，具体格式以实际输出为准：

```text
Lua 堆快照 / PID 12345
抓取时间：2026-11-20T14:00:00Z
暂停耗时：820 ms / 抓取服务：3
解析状态：完整枚举，强引用解析完整，弱引用语义分析未启用

已解析对象分配量：776 MiB
  从已知根确认强可达：682 MiB
  未确认强可达：94 MiB（不能直接判为垃圾）

服务              已解析分配量    确认强可达      主要类型
:01000012         480 MiB         438 MiB         table / string
.gateway          196 MiB         156 MiB         string
.logger           100 MiB          88 MiB         table

大对象 #123 / 服务 :01000012
类型：table
自身大小：8 MiB / 有效条目：180,000
沿强引用可达：286 MiB（含共享对象，各项不可相加）

持有路径 1：
  registry → ["_LOADED"] → ["player.cache"] → ["sessions"] → #123

持有路径 2：
  registry → ["_LOADED"] → ["player"] → ["flush"]
    → function @service/player.lua:86 → upvalue "sessions" → #123

内容摘要：
  ["uid:10001"] → table #124
  ["uid:10002"] → table #125
  ... 展示 2 / 180,000 项

排查线索：大量玩家键由 sessions 表持续持有，可检查退出时的移除逻辑。
单次快照不能证明这些条目已经过期，也不能证明存在泄漏。
```

报告固定顺序：覆盖范围 → 服务排行 → 类型构成 → 大对象和路径 → 未解析情况。
同一对象只建立一份记录，多个持有者列为替代路径。地址作为 inspect 的辅助字段，
主要展示模块名、字段、upvalue 等业务线索。

大对象同时关注自身容量大的表和持有大量子对象的容器。不能只按 table 自身大小
排序，否则会漏掉自身小、挂着许多大字符串或子表的对象。

## 4. 字节数和“持有”的定义

- **自身大小 / shallow bytes**：对象结构及其直接拥有的数组、节点区、字符串内容等。
  按版本布局计算已分配容量，不把仅被引用的对象加进来，不包含 allocator 元数据。
- **沿强引用可达大小 / reachable bytes**：从该对象出发遍历强边，按对象 ID 去重。
  共享对象在不同候选项中可能重复出现，因此不同项目不能相加。
- **独占保留大小 / retained bytes**：需要完整根和引用语义及支配关系分析；第一版不承诺。
- **对象分配量**不等于 RSS：不含原生库外部分配、分配器碎片和其他进程内存。
  Userdata 只计 Lua 可识别的结构、用户值和 payload，不跟随任意 C 指针估算外部内存。

路径中的字段名表示实际 table key；若 key 不是短字符串，显示整数或对象 ID。
引用边标注强、弱、条件引用、运行时管理边；GC 链只是枚举结构，不是业务持有关系。

## 5. 捕获：停止全部线程，再恢复

捕获阶段的流程：

1. 冻结前尽量预载符号、校验输出目录和参数。
2. 用整进程冻结守卫停止所有线程，并确认停止完成；处理新增线程和退出竞态。
3. 枚举 VM，以 `global_State` 去重；同一堆的 coroutine 不能被当成多个堆。
4. 复制对象记录、根和引用数据到快照构建缓冲区，保留离线分析必需的数据。
5. 完成或遇到限制立即恢复进程，再序列化产物和执行路径分析。

Linux 实现候选为 ptrace seize/interrupt 全线程，并在冻结过程中处理线程创建；
具体事件处理和原有 job-control stop 的保存/恢复需要原型验证。不能只停止主线程，
也不能用 SIGCONT 无条件恢复一个原本就被用户暂停的进程。

守卫必须覆盖错误返回、信号取消和部分冻结失败的清理。不能声称 Drop 能处理 SIGKILL；
需单独验证 tracer 意外退出时的恢复行为，避免采用会连带杀死目标的设置。

设置暂停时限、对象数、边数和采集字节数上限。到限恢复并保存带 incomplete 标志的
结果；不能把截断结果称为全堆统计。时限是尽力而为，并非对内核阻塞的硬实时保证。

冻结消除了后续并发写入，但线程可能恰好停在修改 table/GC 链的中间。读取成功不等于
数据结构完整。交叉校验链节点、tag、容量和引用，失败按 VM 标记不完整；不在原地无限
重试，也不悄悄恢复运行后把新读到的数据混进同一份快照。必要时整次重新捕获。
如果实际不完整率过高，再讨论目标配合的安全点，不先引入注入或远程调用。

暂停预算需要实测，堆越大不保证停得越短。全线程暂停时可能阻塞同进程其他业务，
报告必须展示实际暂停耗时和预算是否触发。

## 6. 对象图和可读路径

枚举每个堆的 `allgc`、`finobj`、`tobefnz`、`fixedgc` 等所属链，按地址去重，
防循环并限制访问次数。分代边界指针不能重复作为独立链累计。具体链和头部布局必须
分别通过 5.4/5.5 的真实头文件验证，不能仅复制当前 CallInfo 的布局假设。

解析对象：Table 的数组/哈希键值及 metatable、字符串、Lua/C closure 的 upvalue、
Proto 常量和子 Proto、thread 的有效栈和相关引用、userdata 的 uservalue/metatable。
open upvalue 的值来自目标栈，closed upvalue 来自其存储字段，不能一律按内联值读取。
保留全部有效引用用于图分析；仅裁剪预览文本，不能用现有 4 KiB 预览上限裁剪对象图。

根至少包括 registry、main thread，以及按对应版本 GC 实现确认的运行时根。
GC 对象名单不是根集合。所有 coroutine 的栈也不能无条件设为根，否则会把本来不可达
的 coroutine 及其对象错误地认作存活。终结器对象、固定对象单独建模。

根路径在恢复后通过图遍历生成：优先输出短的、有字段名和源码线索的强路径，限制
每个对象显示的路径数与深度；说明总直接引用数与展示数的区别。路径截断不改变字节统计。
处理循环引用并保持稳定排序，避免每次报告顺序随机变化。

全对象逐个计算 reachable bytes 成本可能接近 O(V×(V+E))，不能直接照做。
先按 shallow bytes、条目数、引用入度及业务容器线索筛出有上限的候选，
再对候选去重遍历，设置分析预算。若预算不足，报告“未计算”，不能显示为 0。
候选筛选可能漏掉分散持有的大容器，报告说明这不是全图精确 retained 排行。

## 7. GC：第一版不假装已经排除垃圾

暂停不会主动回收垃圾；GC 的颜色位也不能跨阶段直接当成此刻业务可达性。
第一版分开输出“枚举到的已分配对象”与“从已知根确认强可达对象”。
没有强路径的对象标成“未确认强可达”，不标成“垃圾”。

弱键表中的 ephemeron 需要条件传播和不动点计算；弱值不能按强边遍历。
首版可以识别并标注这些边，但语义没有完整实现时必须关闭“待回收垃圾”的确定性结论。
终结器、复活和捕获中的 GC 阶段进一步限制垃圾分类；报告逐项说明分析能力。
即便所有读取均成功，也不能用“解析完整”代替“GC 语义完整”。

要真正排除 GC 时机影响，后续实现与对应 Lua 版本一致的根、弱引用和终结语义，
并与目标侧诊断结果交叉验证。另一条路线是应用在安全点 GC 后配合抓取；那是独立的
可选协作模式，不是纯外部模式默认行为。本设计不执行 `lua_gc` 或修改目标内存。

## 8. 模块划分建议

复用平台 reader、符号和 VM 发现能力；不让 CPU `Aggregator` 接管堆分析。

```text
process/freeze.rs       平台冻结守卫和恢复
lua/heap_layout.rs      堆字段与版本布局、类型大小
memory/capture.rs       VM 去重、对象枚举、根与引用采集、预算
memory/snapshot.rs      版本化离线对象图和完整性标记
memory/analyze.rs       强可达、候选排行、路径和摘要
output/memory.rs        文本报告和离线 inspect
```

快照头包含工具版本、格式版本、Lua 布局、指针宽度、端序、时间、选中的服务、暂停耗时、
各类上限、覆盖率和诊断。对象 ID 仅在该快照内有效，不作为跨快照身份。
保存文件使用临时文件再 rename，部分采集与文件写入损坏是两种不同状态。

## 9. 验收与实施顺序

1. **冻结原型**：多线程目标在成功、取消、读失败、线程退出、新建线程、预算耗尽后
   都能继续运行；原本停止的目标保持原状态。先验证捕获是否足够稳定。
2. **5.4 对象枚举与大小**：用真实头文件验证布局；mock reader 覆盖对象链、坏长度、
   回环、重复堆、overflow；目标侧 fixture 对照已知 table/string/coroutine 分布。
3. **引用路径与单次报告**：registry 模块表、open/closed upvalue、共享引用、循环引用、
   无源码信息、超长 key 和截断；同一对象多路径不能重复累计服务总量。
4. **诚实的 GC 分类**：弱表、ephemeron、finalizer、不可达 coroutine 等 fixture 必须
   不会被误报为强持有；未支持的语义显示 unknown。
5. **验收真实 skynet**：大量空闲服务、活跃服务、服务增删，多种堆规模下测暂停时间、
   采集内存和报告生成耗时。验证注册名和 handle 能引导到实际服务。
6. **Lua 5.5**：独立布局校验和同样的 fixtures 通过后开放。

第一版完成标准：用户能通过一份报告定位服务、找到重要容器及其实际持有路径，
并清楚知道报告的覆盖范围。暂不承诺源码分配行、自动泄漏判定、精确独占大小和快照对比。
